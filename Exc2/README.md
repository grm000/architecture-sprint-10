
## Требования

**Промежуточное состояние (через пару месяцев).** MVP, в котором клиент сможет самостоятельно записаться на приём к специалисту через портал компании.

При этом команда ресепшена будет видеть эту запись:

сотрудники смогут отследить запись в системе и за день до приёма напомнить про него и пациенту, и специалисту.

Необходимо определить категории данных пациентов и разнести их по различным доменам.

Для каждой категории данных определить роли (RBAC) или атрибуты (ABAC), на основании которых сотрудникам будет разрешён доступ к данным.

## Решение

**Веб-портал**: клиент сможет самостоятельно записаться на приём к специалисту.

1. Хранение: PostgreSQL с включённым шифрованием (TDE), шифрование файлов AES-256.
2. Транспорт: TLS 1.3, API Gateway с аутентификацией.
3. Сроки хранения: данные удаляются через 3 года после завершения услуг или по запросу клиента.
4. Защита данных: шифрование. Доступ только к своей информации. Тегирование чувствительных данных (PII, Medical).

**CRM**: централизованное управление записями пациентов.

1. Хранение данных: централизованная база данных PostgreSQL.
2. Транспорт: защищённый API Gateway с аутентификацией.
3. Сроки хранения: финансовые данные — 5 лет, записи клиентов — 3 года.
4. Защита данных: ролевой доступ (RBAC), шифрование данных на уровне базы (TDE).

**Платёжный шлюз**: обработка транзакций клиентов.

1. Хранение данных: критические авторотационные данные банковской карты токенезированы, в явном виде не хранятся.
2. Транспорт: TLS 1.3, oAuth 2.0 авторизация, ограничения по IP.
3. Сроки хранения: данные удаляются через 3 года или по запросу клиента.
4. Защита данных: шифрование данных на уровне базы (TDE).

**Интеграция с лабораторией анализов**: получение данных о результатах.

1. Хранение данных: определяет лаборатория
2. Транспорт: TLS 1.3, oAuth 2.0 авторизация, ограничения по IP.
3. Сроки хранения: определяет лаборатория
4. Защита данных: строгие контракты API, минимизация объёма передаваемой информации.
